# 判定専用の模型（Jev のような仕組み）の設計と測定

2026-10-19、枝 `exp/jev-design`。今回は設計と測定だけで、IME への組み込みはしていない。

## ねらい

Jev（TypeSafe AI、2026-09）は、文章を生成せず「決まった選択肢と確率」だけを一度の計算で返す判定専用の模型。
コンパウンドIMEに当てはめると、Mozc（と AzooKey の辞書）が出す候補を並べ、小さな模型が「どれが正しいか」の
確率を一度にまとめて返す形になる。これで、今の変換の本体の生成（all_zenzai。zenz が文全体を1語片ずつ確かめ、
食い違えば格子を絞り直す。最大10回の評価）を置き換えられるかを調べた。

## 結論（先に）

- **上限は十分にある。** 生成なしの候補だけから正解を組める文は 6,985 文のうち 6,052 文（本線 v5 の正解は 4,858 文）。
  本線が正解なのに生成なしの候補からは組めない「生成でしか出ない」文は **130 文（本線の正解の 2.7%）** だけ。
- **今の zenz をそのまま判定に使う案 (a) は、正しさも速さも今に届かない。** 生成なしの候補（辞書の文全体 ∪ 組32）を
  zenz で採点して最大を選ぶと 4,566 文（本線より 292 文少ない）。時間は候補8つで GitHub の計算機 211 ミリ秒、
  手元の PC 72 ミリ秒（4スレッド）で、今の all_zenzai（GitHub で ja400 85、ウィキペディア 235 ミリ秒）より遅いか同じ。
- **おすすめ:** 生成の置き換えはしない。次の一歩は、(1) 測った「語片の木の一括採点」を前後の文での並べ替え
  （contextPriorWinner、1変換あたり評価 2.9 回）に使って時間を減らす、(2) 小さな文字単位の判定器 (c) を
  zenz の点の蒸留で作り、「生成が要るか」の門にする（下の 4、机上で生成を 16% の変換だけに減らせる見込み）。

## 1. 上限（生成なしの候補から正解を組めるか）

材料: 人工知能の重みを渡さずに（生成なし。Mozc と AzooKey の辞書の変換だけ）全部の試験の文を変換し、
`tools/jev_collect.sh` で候補を書き出した（run 39249431055 の collect、成果物 `jev-*`）。本線（v5）の出力は
run 39196977336 の `linux-results`。

候補の集まり（どれにも「人工知能なしの出力」そのものを入れる。半角の ? ! は全角にそろえて比べる＝変換の後の決まった直しと同じ）:

- **文節K**: 今の Mozc の文節の切り方のまま、文節ごとの候補の上位K（K=4、8、16）から1つずつ選んで組む（組み合わせの数は多い）
- **組N**: 同じ候補を Mozc のコストの和の小さい順に並べた文全体の上位N（N=8、32）
- **辞書8 / 辞書全部**: AzooKey の辞書の変換（生成なし）の、読み全体を使い切る文全体の候補。保つ数を 32 にしても

- **全部の和**: 文節16 ∪ 組32 ∪ 辞書全部
- **生成でしか出ない**: 本線は正解、全部の和からは組めない

## 2. (a) 今の zenz v5 で候補を採点だけする（机上の正しさ）

  選ぶ 138 文。逆に、本線が間違いで zenz が正解を選ぶ 189 文。**負けの主な原因は候補の集まりの狭さ**（組32 では

- zenz の選び違いの型: 数の書き方（「10月10日」より「十月十日」や かな書き を好む。今の変換は数の決まった直しで

  選ぶより良くならなかった（差 1 で 4,519、差 2 で 4,448）。

## 3. 速さ（候補 K 個を一度に採点する時間）

方式（`tools/jev_score.cpp`）:

- **語片の木（trie）**: 問いと、候補どうしで共通の語片の前半を1回だけ並べ、全部を1回の評価にする。
  各語片に「その語片を通る候補の列の番号」を全部付ける（llama.cpp の1つの語片に複数の列を持たせる）。
- **写し（flat）**: 問いを1回評価して列に写し、全候補の語片を1回の評価にまとめる。
- **順に（seq）**: 問いを1回評価し、候補を1つずつ評価する（今の選び手の採点 ScoreSentenceSuffixes と同じ形）。
- **使い回しなし（full）**: 候補ごとに問いから評価する。

日本語だけの400文の先頭150文と、ウィキペディアの文150文（K=32 は候補が32以上ある 291 文）。平均ミリ秒（括弧は評価した語片の数の平均）。

GitHub の計算機は AMD EPYC 7763、4つ（run 39249431055 の bench）。手元は Ryzen 7 8840U（公式の Windows 版 b11327 を
mingw の g++ で直接つないで同じ道具を組み立てた）。llama-batched-bench（`--override-kv tokenizer.ggml.pre=str:default`）の
一括評価の速さは、GitHub 3スレッドで 1秒あたり約 950 語片、手元 8スレッドで約 3,500〜4,000 語片（手元は約3.5倍速い）。

今との比べ:

- 今の all_zenzai（run 39196977336 の組 p、GitHub 3スレッド、変換エンジンの llama.cpp b4846）は 1変換あたり平均
  ja400 85.5、ウィキペディア 234.8、前の文なし 253.5、前の文あり 334.6 ミリ秒（評価 1.4〜2.3 回、1回あたり新しく
  計算する語片 21〜57）。上の150文＋150文に当てると約 160 ミリ秒。
- 判定の形は、候補4つ（木 127 ミリ秒）なら今より少し短いが、候補8つ（211）で 1.3倍、候補32（543）で 3.4倍かかる
  （変換エンジンの llama.cpp と版が違うので目安。同じ版での all_zenzai 相当の仕事＝評価2回の「順に K=2」は 138 ミリ秒）。
  all_zenzai は多くの文で評価1〜2回で済むため、全部の候補の語片を計算する判定の形は、同じ zenz では速くならない。
- 語片の木は、順に採点するより 候補8つで 45%、32 で 60% 速い（GitHub）。今の選び手と前後の文での並べ替えの採点は
  「順に」の形なので、ここはすぐ速くできる。

## 4. 生成でしか出ない書き方を補う案

1. **判定してから、自信がないときだけ生成に戻る。** 机上（辞書全部∪組32 を zenz で採点）で、最高点を1字あたりにした値が
   -0.1 未満の文だけ本線（生成）に戻すと、正解 4,823（本線 4,858 の 35 文少ない）で、生成に戻るのは変換の 15.8%。
   -0.05 なら 4,829 で 22.1%。ただし門に zenz を使うと門だけで all_zenzai と同じくらいかかるので、門は (c) の小さな模型で
   作る必要がある（下の 5）。値は試験の文で振ったもので、採るときは学習用の文で決め直す。
2. **候補の集まりを広げる。** 組を 128 まで並べると上限は 5,732。語片の木なら候補が増えても共通部分は1回で済む
   （K=16→32 で語片は 1.7倍）。文節の形（文節ごとに選ぶ、今の選び手の形）なら上位8で 5,755 と組より効率が良い。
3. **英字の文節は判定に入れない。** 本線と同じく、確定済みの英単語は左右の文脈として渡し、日本語の部分だけを判定する。
4. **数・記号は判定の後の決まった直しに任せる。** 数の書き方の違いは候補から外すか同じ扱いにする。

## 6. おすすめと次の一歩

- **生成（all_zenzai）の置き換えはしない。** 同じ zenz で判定の形にすると、正しさは 292 文少なく、時間も候補8つ以上では長い。
- **次の一歩（小さく測れる順）:**
  1. 前後の文での並べ替え（contextPriorWinner。組 p の clause-with で変換の 48% に入り、1変換あたり評価 2.9 回、平均 205 ミリ秒）と
     選び手の採点を、語片の木の一括採点に替える。机上では候補3〜4つで「順に」の 6割程度の時間。出力は変わらない
     （点の差は丸めの範囲。optimization-adoption の手順で出力不変を確かめてから採る）。
  2. (c) の小さな判定器を、学習用の文の候補と zenz の点で蒸留し、「人工知能なしの出力でよいか／生成が要るか」の門にする。
     zenz を門にした机上の見込み（生成 16%、正解 −35）にどこまで近づくかを、学習用の文で先に測る。
  3. (b) は (c) の門の後、候補の集まりを組128 か文節の形に広げてから考える。

## 再現

```
# 材料（人工知能なしの候補）と採点と時間: exp/jev-design に push すると Linux test から jev-data.yml が動く
python tools/jev_ceiling.py report <jev-* をまとめたフォルダ> tests/conversion <linux-results> [<jev-score-*>]
python tools/jev_ceiling.py jobs   <同上> tests/conversion <linux-results> jobs/jobs.tsv jobs
python tools/jev_ceiling.py bench  <jev-bench> [先頭の文の数]
jev_score <model.gguf> <jobs.tsv> <out.tsv> <スレッド数> trie,flat,seq,full [候補の数の上限]
```

足した仕組み（どれも環境変数や試験用の命令を決めたときだけ動き、普段の変換は変えない）:
`tools/apply_jev_dump.py`（文節ごとの候補の数 MYIME_JEV_DUMP_K、文全体の候補 MYIME_JEV_WHOLE、AzooKey の保つ候補の数
MYIME_JEV_NBEST、試験用の道具の命令 JEV_MARK）、`tools/jev_collect.sh`、`tools/jev_score.cpp`、`tools/jev_ceiling.py`、
`.github/workflows/jev-data.yml`。exp/jev-design の枝では、計算機を回すため通常の試験（test、results）は流さない。

注意:

- 試験の文は学習に使っていない（(a) は学習なし。4 の値は試験の文で振ったもので、採るときは別の文で決め直す）。
- zenz は問いの読みの後に U+EE01 ではない印（U+EE08 らしい）を高い確率で予想した。生成させると正しく変換するので
  今回の比べには影響しないが、組み込むときは変換エンジンの実際の問いの形（ZenzPromptBuilder）を写して確かめる。
- 手元の時間は 1回だけの測定で、PC のほかの処理の影響を受ける。
